# 下一阶段开发计划：实时房间服务 MVP

## 1. 阶段目标

将当前可独立运行的规则引擎接入一个服务端权威的实时房间服务，使四个模拟客户端可以完成：

1. 创建并加入房间；
2. 准备和开始比赛；
3. 接收各自可见的牌局快照；
4. 提交摸牌、出牌、吃碰杠胡等操作；
5. 经过服务端版本与规则校验后同步结果；
6. 断线后恢复到正确状态；
7. 完成单局计分、多局累计和总结算。

本阶段先使用内存存储跑通完整联机流程，再接入 PostgreSQL 和 Redis，避免数据库细节阻塞房间协议验证。

## 2. 交付范围

### 2.1 实时服务工程

建立 `apps/realtime-server`：

- Node.js + TypeScript；
- 原生 WebSocket 或轻量 WebSocket 库；
- 房间注册表；
- 连接与玩家会话映射；
- 命令分发器；
- 公开事件和私有事件发送器；
- 心跳、断线检测和优雅关闭。

### 2.2 房间聚合

实现 `RoomAggregate`，统一持有：

- 房间 ID 和短房间号；
- 房主与四个座位；
- 玩家准备状态；
- 房间规则快照；
- `MatchEngine`；
- 当前 `SingleRoundEngine`；
- 房间版本号；
- 已处理的 `requestId`；
- 当前响应窗口定时器。

房间聚合是唯一可以修改比赛和单局引擎的入口，WebSocket 处理器不能直接操作手牌。

### 2.3 命令处理

首批支持：

- `room.create`
- `room.join`
- `room.ready`
- `room.leave`
- `game.draw`
- `game.discard`
- `game.claim`
- `game.kong.concealed`
- `game.kong.added`
- `game.kong.react`
- `game.win.selfDraw`
- `game.reconnect`

每条命令必须校验：

- 登录会话；
- 房间和座位；
- `requestId` 幂等；
- `expectedVersion`；
- 当前阶段；
- 当前操作者；
- 规则合法性。

### 2.4 事件可见性

建立服务端事件映射层：

- 摸到的牌面只发送给摸牌玩家；
- 其他玩家只收到“某座位已摸牌”；
- 手牌快照只对本人可见；
- 响应窗口结束前不公开其他人的选择；
- 出牌、副露、结算等公共信息向全房广播；
- 管理员审计事件与玩家事件分离。

不能直接把规则引擎的内部事件原样广播。

### 2.5 定时器和自动操作

- 出牌倒计时；
- 吃碰杠胡响应倒计时；
- 超时自动过牌；
- 玩家离线后的短期等待；
- 超过等待时间后自动托管；
- 定时器回调必须携带状态版本，过期回调不得修改新状态。

### 2.6 快照与重连

重连快照包含：

- 房间与座位信息；
- 比赛总分和当前庄家；
- 单局阶段、当前座位和剩余牌数；
- 公共弃牌和副露；
- 当前玩家自己的手牌；
- 当前玩家可执行的操作；
- 当前版本与事件序号；
- 倒计时截止时间。

客户端收到快照后应覆盖本地牌局状态，再继续应用后续增量事件。

## 3. 实施顺序

### 里程碑 A：内存房间服务

- 创建实时服务工程；
- 完成连接、房间、座位和准备；
- 接入现有规则引擎；
- 四个测试客户端跑通一场比赛；
- 实现公开/私有事件映射。

验收标准：自动化集成测试可以让四个客户端完成建房、开局、若干回合和总结算。

### 里程碑 B：超时与重连

- 操作截止时间；
- 自动过牌；
- 托管策略；
- 快照生成；
- 断线重连；
- 旧版本和重复命令处理。

验收标准：随机断开一个客户端后重新连接，手牌、轮次、分数和倒计时均与服务器一致。

### 里程碑 C：事件持久化

定义存储接口：

- `RoomRepository`
- `GameEventStore`
- `SnapshotStore`
- `IdempotencyStore`

先提供内存实现，再增加 PostgreSQL/Redis 适配器。

验收标准：实时服务进程重启后，可以从快照和增量事件恢复未结束牌局。

### 里程碑 D：微信登录 API

建立 `apps/api-server`：

- 微信登录 code 换取会话；
- 本地用户和短期访问令牌；
- WebSocket 连接票据；
- 战绩和牌局详情接口；
- 基础限流和审计日志。

验收标准：只有有效的服务器签发票据能够加入实时服务。

## 4. 测试计划

- 房间创建、加入、满员和重复加入；
- 非当前玩家操作；
- 重复 `requestId`；
- 过期 `expectedVersion`；
- 多人同时响应；
- 响应窗口超时；
- 断线发生在摸牌、出牌和抢杠窗口；
- 私有手牌不会发送给其他座位；
- 单局和比赛分数保持零和；
- 房间完成后释放定时器和连接引用；
- 进程恢复前后事件序号连续。

## 5. 暂不进入本阶段

- Cocos Creator 正式牌桌 UI；
- 运营后台；
- 语音聊天；
- 排行榜和活动；
- 金币、充值或提现；
- 多区域部署。

这些工作应在实时房间协议稳定后开始。

## 6. 规则依赖

以下规则确认不阻塞实时服务骨架，但上线前必须确定：

- 各牌型正式番数；
- 一炮多响；
- 过胡；
- 连庄和局数计算；
- 流局赔付；
- 超时托管的默认动作。

服务端必须在创建房间时保存完整规则与计分配置快照。
