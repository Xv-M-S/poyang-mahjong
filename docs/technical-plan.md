# 鄱阳麻将微信小游戏技术方案

> 文档状态：初稿  
> 适用范围：首个可联机对局版本（MVP）及后续正式运营版本

## 1. 项目目标

开发一款支持四人实时联机的鄱阳麻将微信小游戏，首期重点完成：

- 微信授权登录与玩家基础资料；
- 创建房间、加入房间、邀请好友；
- 四人实时对局、断线重连和对局结算；
- 将鄱阳麻将规则实现为可测试、可配置的独立规则引擎；
- 保存牌局日志和回放数据，便于纠纷定位与规则验证；
- 提供基础运营后台，用于玩家、房间、牌局和配置管理。

首期不建议加入金币交易、充值、提现、排行榜奖励等复杂运营系统。应先保证规则正确、联机稳定和审核合规。

## 2. 产品形态与技术选型

建议使用“微信小游戏”，而不是普通微信小程序。麻将桌需要大量精灵渲染、动画、音效和高频交互，小游戏运行环境更适合游戏循环、Canvas/WebGL 渲染和资源管理。

| 模块 | 推荐技术 | 用途 |
|---|---|---|
| 游戏客户端 | Cocos Creator 3.x + TypeScript | 微信小游戏构建、牌桌渲染、动画与资源管理 |
| 实时服务 | Node.js + TypeScript + WebSocket | 房间、对局状态同步、断线重连 |
| HTTP 服务 | NestJS | 登录、用户、战绩和运营接口 |
| 规则引擎 | 独立 TypeScript 包 | 发牌、出牌合法性、吃碰杠胡与计分 |
| 主数据库 | PostgreSQL | 用户、房间、牌局、结算和配置 |
| 缓存 | Redis | 在线状态、房间索引、短期会话和分布式锁 |
| 对象存储 | 腾讯云 COS | 静态资源和归档回放 |
| 运营后台 | Vue 3 + TypeScript | 牌局查询、规则配置和运营管理 |
| 部署 | Docker + 腾讯云 | API、WebSocket、数据库和监控部署 |

前后端统一使用 TypeScript，规则模型、协议类型和错误码可以共享，减少联调歧义。

## 3. 系统架构

~~~mermaid
flowchart LR
    C["微信小游戏客户端"] -->|HTTPS| A["HTTP API"]
    C -->|WSS| G["实时网关 / 房间服务"]
    A --> U["用户与战绩服务"]
    G --> R["规则引擎"]
    G --> P["牌局与回放服务"]
    U --> DB[("PostgreSQL")]
    P --> DB
    G --> RD[("Redis")]
    P --> COS[("COS 归档")]
    O["运营后台"] --> A
~~~

系统采用“服务器权威”模式：

- 客户端只提交操作意图，例如出牌、碰、杠、胡；
- 服务器校验轮次、牌权、手牌和规则；
- 洗牌、发牌、摸牌、计时和结算均由服务器决定；
- 客户端只根据服务器事件更新画面；
- 每个动作写入牌局事件流，支持重连、回放和审计。

不能让客户端直接提交“我已经胡了”或“我的最终手牌是这些”并由服务器接受，否则容易产生作弊和状态分叉。

## 4. 仓库组织

建议采用 Monorepo：

~~~text
poyang-mahjong/
├─ apps/
│  ├─ game-client/        # Cocos Creator 微信小游戏
│  ├─ api-server/         # NestJS HTTP API
│  ├─ realtime-server/    # WebSocket 房间与牌局服务
│  └─ admin-web/          # Vue 运营后台
├─ packages/
│  ├─ game-rules/         # 鄱阳麻将规则引擎
│  ├─ protocol/           # 消息协议、DTO、错误码
│  ├─ shared/             # 通用工具和类型
│  └─ config/             # 共享工程配置
├─ docs/
│  ├─ rules/              # 规则原文、图片转录与待确认项
│  ├─ protocol/           # 通信协议
│  └─ technical-plan.md
├─ tests/
│  ├─ rule-cases/         # 规则黄金用例
│  └─ load/               # 并发和稳定性测试
└─ deploy/
   ├─ docker/
   └─ scripts/
~~~

依赖方向保持单向：客户端和服务器可以依赖 game-rules 与 protocol，规则包不能依赖 UI、网络或数据库。

## 5. 规则引擎设计

### 5.1 牌模型与模块边界

每张实体牌使用唯一 ID，牌面类型单独编码。即使四张牌牌面相同，其 ID 也不同，以便准确记录摸牌、出牌并生成可复现回放。

规则引擎拆分为：

- **TileSet**：牌集合、编码和排序；
- **WallBuilder**：建牌墙、使用安全随机数洗牌；
- **TurnValidator**：验证当前玩家和动作合法性；
- **ClaimResolver**：处理多人同时吃、碰、杠、胡的优先级；
- **HuDetector**：判断基础牌型是否成胡；
- **PatternEvaluator**：识别鄱阳麻将特有番型；
- **ScoreCalculator**：计算番数、输赢分和封顶；
- **RoundSettlement**：生成单局结算；
- **MatchSettlement**：生成整场结算。

### 5.2 胡牌判断与配置化

胡牌判断分两层：先判断基础结构，再识别鄱阳麻将地方番型。地方规则以独立评估器注册，不散落在网络或 UI 代码中。

以下内容必须配置化：

- 局数、底分和封顶；
- 是否允许一炮多响；
- 吃、碰、杠、胡的优先级；
- 可胡牌型、番数、叠加和互斥；
- 自摸、点炮和杠分结算方式；
- 房主解散、超时托管和离线处理；
- 规则版本号。

每场对局创建时保存完整规则快照。运营后台以后修改规则，也不能改变历史牌局的回放和结算结果。

### 5.3 规则验证

仓库中的规则图片应先转录成结构化规则文档，再建立“黄金测试用例”。每种牌型至少包含：

- 一个合法胡牌示例；
- 一个只差一张但不能胡的反例；
- 与其他牌型叠加时的计分示例；
- 自摸、点炮、杠后等不同上下文；
- 边界案例和冲突优先级。

规则存在口述差异时，建立“待确认规则清单”，由熟悉当地玩法的人逐项确认后再编码。

## 6. 实时对局设计

### 6.1 状态机

~~~text
WAITING
  -> READY
  -> DEALING
  -> PLAYING
  -> REACTION_WINDOW
  -> ROUND_SETTLEMENT
  -> MATCH_SETTLEMENT
  -> CLOSED
~~~

任何客户端命令只有在指定状态下才有效。例如，只有当前操作者能在 PLAYING 状态出牌；其他玩家只能在 REACTION_WINDOW 内响应吃、碰、杠、胡。

### 6.2 消息协议与幂等

客户端命令包括 room.create、room.join、room.ready、game.discard、game.claim、game.pass、game.reconnect 和 room.dissolve.vote。

服务器事件包括 room.snapshot、game.started、game.tile.drawn、game.tile.discarded、game.claim.options、game.claim.resolved、game.round.settled 和 game.match.settled。

每条命令包含 requestId、roomId、roundId、expectedVersion 和 payload。requestId 用于幂等去重，expectedVersion 用于发现客户端状态过期；服务器事件按房间维护单调递增的 version。

### 6.3 抢操作与重连

玩家出牌后，服务器统一计算其他玩家可用操作，开启固定响应窗口，收集操作或超时“过”，再按规则优先级裁决并广播唯一结果。不能以“服务器先收到谁的请求”为裁决依据，因为网络延迟会造成不公平。

重连时，服务器下发公共牌桌状态、当前用户私有手牌、事件序号、当前操作者、剩余倒计时和可执行操作。客户端以服务器快照覆盖本地状态，再应用快照后的增量事件。

## 7. 登录、用户与房间

登录流程：

1. 客户端调用 wx.login() 获取临时 code；
2. 服务端使用 code 换取微信侧会话标识；
3. 服务端创建或查找本地用户；
4. 服务端签发短期访问令牌和可刷新会话；
5. WebSocket 建连时再次鉴权。

敏感凭据只能放在服务器环境变量或密钥管理服务中，不得写入客户端包或 Git 仓库。

房间号使用短期随机码并设置有效期。加入房间时检查房间状态、规则版本、人数上限、重复席位和封禁状态。

## 8. 客户端设计

首期页面包括：启动与资源更新、微信登录、大厅、创建/加入房间、等待房间、麻将牌桌、单局结算、总结算、战绩详情、设置与帮助。

客户端内部按 View、ViewModel、Network、Store、Protocol 和 Assets 分层。牌桌动画只能作为表现层；动画尚未结束时收到新状态，应进入事件队列并最终与服务器版本一致。

## 9. 数据与回放

核心表包括 users、rooms、room_players、matches、rounds、game_events、settlements、rule_sets、login_sessions 和 admin_audit_logs。

每个关键操作作为只追加事件保存，至少记录 matchId、roundId、sequence、actorId、type、payload、serverTime 和 stateHash。回放由初始随机种子、规则快照和有序事件重建。

玩家默认只能看到自己当时可见的信息；管理员查看完整牌局必须经过授权并记录审计日志。

## 10. 安全、合规与反作弊

- 服务端生成洗牌随机数和牌墙；
- 所有动作进行权限、轮次和规则校验；
- 访问令牌短期有效，并支持设备会话失效；
- HTTP 与 WebSocket 全程使用 TLS；
- 对登录、建房、入房和动作接口限流；
- 关键事件保存状态哈希，检测回放数据被修改；
- 日志不记录微信会话密钥、令牌和完整个人信息；
- 管理后台采用独立域名、强认证和角色权限；
- 对频繁断线、异常操作速度和多账号同设备进行风险标记；
- 遵循微信平台规则以及适用的隐私、未成年人和网络游戏管理要求。

项目定位为休闲娱乐，不设计现金兑换、赌博性筹码或变相提现功能。

## 11. 部署与运维

至少划分 development、staging、production 三套环境，并使用独立数据库、Redis、密钥和微信配置。

MVP 可部署一个 API 服务和一个实时服务。并发增长后，API 服务无状态水平扩容；同一房间固定由一个实时节点负责；Redis 保存连接路由和房间节点索引；节点退出前停止接收新房间并等待存量牌局结束。

必须监控：登录成功率、接口延迟、WebSocket 连接数与重连率、活跃房间数、对局完成率、动作处理延迟、数据库慢查询、规则异常、状态版本冲突、结算失败和客户端崩溃率。

严重告警应包含房间 ID、牌局 ID、规则版本和事件序号，避免只记录无法定位的错误文本。

## 12. 测试策略

| 测试层级 | 重点 |
|---|---|
| 单元测试 | 胡牌、番型、计分、优先级、状态转换 |
| 属性测试 | 牌数量守恒、不重复发牌、分数结算守恒 |
| 协议测试 | 客户端与服务端消息兼容性 |
| 集成测试 | 登录、建房、开局、完整牌局、解散 |
| 弱网测试 | 延迟、乱序、丢包、重复请求和重连 |
| 压力测试 | 大量在线连接、房间创建和同时结算 |
| 真机测试 | 微信版本、安卓/iOS、异形屏和低端设备 |

规则引擎应支持在不启动客户端和数据库的情况下独立运行测试。任何规则修复都必须先增加一个能复现问题的测试用例。

## 13. 开发阶段与工期

### 阶段一：规则定稿与技术骨架（1～2 周）

完成规则图片转录、待确认项、Monorepo、代码规范、CI、牌模型、协议、状态机和基础胡牌测试。

### 阶段二：单机可玩原型（2～3 周）

完成牌桌 UI、发牌、摸牌、出牌、吃碰杠胡和结算，用本地机器人跑通完整牌局，并邀请当地规则确认人验收。

### 阶段三：联机 MVP（3～4 周）

完成微信登录、房间、WebSocket、服务器权威状态机、抢操作、重连、战绩和回放，并进行弱网与多人真机测试。

### 阶段四：上线准备（2～3 周）

完成运营后台、监控、告警、审计、压力测试、安全与隐私检查、资源优化和灰度发布。

以上周期按 2～4 人且熟悉 TypeScript 和 Cocos Creator 的团队估算；规则反复修改、素材制作和平台审核可能影响实际进度。

## 14. 开发前必须确认的规则

1. 使用哪些牌，是否包含风牌、箭牌或花牌；
2. 庄家产生方式、连庄和换庄条件；
3. 是否允许吃牌，吃牌座次限制；
4. 碰、明杠、暗杠、补杠的条件与分数；
5. 是否允许抢杠胡、一炮多响、过胡限制；
6. 所有合法胡牌牌型、番数、叠加和互斥关系；
7. 自摸、点炮、杠上开花、海底等结算方式；
8. 底分、封顶、包赔和流局规则；
9. 超时、离线、托管和解散房间规则；
10. 一场的局数以及总分相同时的处理方式。

这些内容应形成版本化的规则配置和验收用例，不能只保存在聊天记录或口头约定中。

## 15. 建议的下一步

1. 将现有规则图片整理为可检索的规则 Markdown；
2. 建立待确认问题和典型牌例；
3. 实现纯 TypeScript 规则引擎及测试；
4. 用本地模拟器跑通一局；
5. 再接入 Cocos 客户端、WebSocket 和微信登录；
6. 最后补齐后台、监控与上线配置。

第一项可交付开发成果应是“规则引擎测试全部通过”，而不是一个只有界面但无法证明结算正确的牌桌。
